# @knobs/extension

A Chrome extension that puts the devknobs panel on any page, the same panel as the npm package, with some of its knobs set for real through the Chrome DevTools Protocol (`chrome.debugger`) in place of devknobs' emulation in the page.

Install it from the Chrome Web Store: <https://chromewebstore.google.com/detail/knobs/cpdmafeojnbdnnhldafobkaajiemcidj>. The build steps below are for development.

What it does, how to install it, what Chrome sets for real and the permissions are in the user docs: <https://knobs.dev/docs/extension>. The full reference is at <https://knobs.dev/llms-full.txt>. This file is for working on it.

## How it fits together

- `src/content.ts` runs in the page's own world (`world: "MAIN"`, at `document_start`, in the top frame and in devknobs' width frame), so `window.devknobs` is there for agents as with the npm package. It mounts devknobs with a native driver that sends the knobs Chrome sets for real (text size, offline, the preferences, a plain viewport, the user agent) on, and with no handle on the page's edge, since the toolbar button opens the panel (the panel's settings can show it again).
- Pages that run devknobs themselves. The content script mounts with `host: true`, and before any page script, so its copy holds the page as the host (`Symbol.for("devknobs.host")` beside devknobs' `devknobs.owner` slot on `window`). A copy the page mounts later finds it and puts up no panel: it hands over its `hotkey`, `grabKey`, `grab`, `open` and `grabColor`, and its `unmount()` leaves the extension's panel. `window.devknobs` stays the extension's. The page's early script, inlined in its `<head>`, finds the page held and patches nothing. A copy that knows no hosts (devknobs 0.3.0 and older) takes the page as a hot update would; the extension's copy then takes it back through that copy's own way out, up to three times per page load, then leaves it to the page with a warning in the console. Prefer, in the panel's settings, can give such a page to its own copy instead, a local build say: `PREFER_KEY` in `chrome.storage.local`, kept for the profile by the service worker. The bridge reads it straight from storage as the page starts and hands it to the page as a `prefer` message, and on each change. It can come in after the page's copy mounted, so the handover works whenever it arrives: a copy that knows it leaves the host a way to take the page (`adopt`'s `take`), and the host, preferring the page, unmounts (its native knobs go back to Chrome's) and calls it; the page's copy then mounts as with no host, its settings showing prefer, and the host does not take the page back (nor from a copy that knows no hosts). The content script marks the top window, so devknobs' frame leaves the page to the page's copy there too. Back to the extension from the page's panel loads the page again. A load after a handover starts the extension's copy with `persist: false` (a flag in the tab's `sessionStorage`, read as the load starts), so it neither reads nor overwrites the stored knobs the page's copy shares. Where the page unmounts its copy after a handover, the toolbar button mounts the extension's copy again, open. Any script of the page can send the prefer message through the bridge, as it can the knobs, the user agent and the bypass: the worst it does is pick who runs the panel.
- Two copies of the extension on one page, such as the store's and a local build. Each build's page world and bridge talk on event names of their own (`KNOBS_CHANNEL`, random per build), so neither hears the other's. The content script mounts with `build` (`KNOBS_BUILD`: `local` where the build has a label, else `store`), which devknobs puts on the host slot as its rank: a local build outranks a store one, then the newer version, then the version as text. A host that finds a higher one holding the page does not claim it and stands down (`stoodDown`: the content script stops hearing its bridge, has its service worker drop the tab's user agent and any knobs it kept for the tab, which takes its debugger off, and its toolbar button toggles the holder's panel); one that finds a lower one claims, and the lower one, released, stands down instead of taking the page back. The holder hears it (`outranked`) and its footer adds `store extension stood down`. The store's 0.5.1 and older publish no rank, rank lowest, take the page from any copy as they mount and take it back only from copies with no host slot: a local build takes it back from them once, and stops their bridge's messages (the one old event name) at `window` while it holds the page. What such a copy kept for the tab from an earlier load (its knobs through the debugger, its user agent rules) stays until the tab closes or that extension is turned off: new code cannot reach it. A rank a host cannot read, a later build's, outranks it, so two hosts never take the page from each other in turn. The tab's yielded flag is read by every copy and cleared at `DOMContentLoaded` by the one that holds the page.

| On the page                               | Who runs the panel                                                               |
| ----------------------------------------- | -------------------------------------------------------------------------------- |
| the page's copy only                      | the page's                                                                       |
| the store extension only                  | the extension's                                                                  |
| the store extension and the page's copy   | the extension's; the page's with prefer set to page                              |
| a local extension and the page's copy     | the extension's; the page's with prefer set to page                              |
| the store extension and a local extension | the local extension's; the store's stands down                                   |
| all three                                 | the local extension's; the page's with prefer set to page in the local extension |

- `src/bridge.ts` runs in the extension's world in the top frame and carries them between the page and the service worker, as json on `document` events (the page world cannot reach `chrome.runtime`).
- Shortcuts. The keys the user sets in the panel are kept for every site: `KEYS_KEY` in `chrome.storage.local`, not the page's `localStorage`. The content script hands devknobs a `keysStore`; the bridge reads the key as the page starts and on each change and sends a `keys` message, and devknobs, started from the defaults, takes them then. A key set goes to the service worker as a `keys` ask, which the bridge passes only during a user gesture (`navigator.userActivation.isActive`), as with real phone mode: a page script can change them only right after you click or press a key on that page; otherwise its change stays in its tab. devknobs' frame, which has no bridge, reads the store of the extension's copy on the page above. Keys a page's `localStorage` kept before are not brought over. Where the page's own copy runs the panel, it keeps its own keys in `localStorage`.
- Edits kept after a reload. The Elements view's `keep edits after reload` switch keeps a page's edits in `chrome.storage.local`, not the page's `localStorage`: one key per page, `edits:` then its origin and path (`EDITS_PREFIX`, `editsKey` in `src/messages.ts`), holding devknobs' kept json and `at`. The content script hands devknobs an `editsStore` (top frame only: devknobs' frame keeps none); the bridge reads the page's key as the page starts and on each change and sends an `edits` message, and devknobs makes them again once it has them and the page settled. A change goes to the service worker as an `edits` ask with the page's path, which the bridge passes only during a user gesture, as with the shortcuts, so a page script's `setEdits()` stays in its tab. Every field is read strictly (`readKept`: at most 200 edits, 256 KB, known kinds only, none that could run a script), by the bridge as it reads storage and, through `readPageMessage`, by the bridge and the service worker for each ask. The service worker takes the origin from the sender, never the message, and keeps 20 pages at most, forgetting the one kept longest ago (`editsToForget`). devknobs never makes an html or attribute edit as the page loads: they wait in the panel for a click on `apply`. Turning the switch off removes the page's key.
- `src/ua.ts` maps a user agent to the request headers the rules set and to the debugger's override.
- `src/background.ts` keeps each tab's knobs, maps them to commands (`src/knobs.ts`) and attaches or detaches the debugger. On each page load the bridge asks for the tab's knobs, and those win over the page's stored ones, so a page on another origin shows what the tab has. The toolbar button opens the panel in the tab; closing it from there resets every knob for the tab, so its rules go, and a page that loaded under a user agent rule loads again. Closing Chrome's debugging bar switches every tab to in-page mode (see [what Chrome sets for real](https://knobs.dev/docs/extension#what-chrome-sets-for-real)); the debugger leaving a tab for another reason, such as the tab closing, puts the panel's knobs back to their defaults.
- The panel keeps the user's own look. The emulated scheme and motion reach every media query in the tab, the panel's too, so `src/offscreen.ts`, an offscreen document outside every tab, reads the real ones. The service worker hands them out with each page load's knobs and sends each change to every tab, and the bridge passes them to devknobs' `setSystemMedia`.
- Framing. The width knob, or a docked panel, loads the tab's own page in a frame, which `X-Frame-Options` or a `frame-ancestors` policy refuses. Only while devknobs' frame is open, two session rules for the tab (`declarativeNetRequest`, the first's id the tab id) have frame loads in that tab, to and from the page's host, lose `X-Frame-Options`, and `Content-Security-Policy` where it has `frame-ancestors` but not `frame-ancestors 'self'` (the rule's `responseHeaders` and `excludedResponseHeaders` conditions, Chrome 128 and up): a policy with `frame-ancestors 'self'`, or with no `frame-ancestors`, stays whole, and one that lists hosts but not `'self'` (`frame-ancestors https://a.example`) is removed, even where it names the page's own host. The frame's address is set by the bridge, from the extension's world, which the page's own `frame-src` does not bind (devknobs' `native.load`; the bridge loads only a frame named `devknobs-frame` and only an address on the page's origin). Chrome holds every later load of the frame to that `frame-src` too, a link clicked in it or devknobs reloading it, so the bridge keeps Chrome's own `securitypolicyviolation` (trusted, enforced, `frame-src`, `child-src` or `default-src`, an address on the page's origin), and when devknobs' frame lands on Chrome's error page within a second of it, loads that address in the frame from its own world, up to 3 times per address in 2 seconds. A frame of the page's own, or a policy that only reports, leaves devknobs' frame be. A form's POST so refused loads again as a GET. The page says so as the frame opens, and the frame's first load waits for the rule (devknobs' `native.framed` holds it), so a new tab with knobs that frame it loads the first time. The rule goes as the frame closes, as the tab loads another page (`webNavigation.onBeforeNavigate`) and with the tab.
- A service worker's frame. Where the page's service worker answers the frame's load, the load the rule sees is the worker's own `fetch`, which belongs to no tab, so the rule above misses it. While a tab has devknobs' frame open on a host (the page tells the service worker as the frame opens and goes), two more session rules take `X-Frame-Options`, and the CSP as above, off what that host's service worker fetches from it: no tab (`tabIds: [-1]`), the host as request and initiator, type `xmlhttprequest` (the type a worker's `fetch` has; `sub_frame` and `other` do not match it). Two rules per host, their ids any free ones, gone once no tab has a frame open on the host, a tab closing or loading another page included. The cost: meanwhile, every answer that host's service worker fetches from the network loses those headers, not only the frame's page. The frame can start loading before the rule is set, and a service worker can answer from a copy it saved, refusing frames, while it saves a new one from the network behind it (X's does): that fetch goes through the rule, so the next load is let in. So a refusal on a page with a service worker loads the frame again after 1 second, then after 3 more, with the notice hidden, before it shows.
- Why a frame was refused. While the debugger is on a tab, the service worker keeps the last few document loads of the tab's frames under the top one (`src/refusal.ts`): the address asked for and where it ended (another host, or Chrome's error page), each redirect, the status, the headers that bear on framing (`X-Frame-Options`, the `frame-ancestors` part of the CSP, `Cross-Origin-*`, `Location`), `Sec-Fetch-Dest` and `Sec-Fetch-Site` as sent, whether a service worker answered and from where, how the load failed (`blockedReason`, the CORS error), and Chrome's own issues (`Audits`) and console lines (`Log`) about it. When devknobs shows its refusal notice, the panel asks for the frame's latest load and says why under the notice in a line, such as `x.com/i/flow/login answered 200 with X-Frame-Options: DENY (from a service worker)` or `redirected to another site: accounts.google.com`, with a "copy details" button for the whole record as json. A service worker's scope comes from the page's own registrations, since the protocol does not give it to an extension. With no knob keeping the debugger on, as for a mocked phone, the line says it was not watching, and "find out why" puts it on, loads the frame again and takes it off once it has the answer. In-page, the line says to turn real browser settings on.
- Past the service worker. A service worker that answers the frame from its own cache sends the refused page itself, which no rule reaches. On a page with a service worker still refused after the loads again, the notice names the cause, then says the site's service worker serves a saved copy of the page that refuses frames, and offers "load past the service worker (Chrome shows a bar meanwhile)": the debugger goes on the tab, `Network.setBypassServiceWorker` has the tab's loads, the frame's and the page's own, go to the network, and the frame loads again. It stays so while the frame is open, and through a load of the tab's page on the same host, such as a page that reloads itself once the frame's copy updates its service worker: the page's stored knobs open the frame again, and the bypass waits 15 seconds for it. Once the frame goes, service workers answer again and the debugger leaves, unless a knob keeps it.
- Leaving the frame. A link, form or script in the frame that goes to another origin (a sign-in provider, say, which refuses frames anyway) takes the whole tab there, as it would with no frame; the knobs wait on the page's origin for the way back. A server's redirect of the frame's first load to another host of the same site, by the same scheme (its last two labels, or three under a public second level such as co.uk; a customer's name under a shared host such as github.io is its own site), such as a site that sends a phone to its mobile host, takes the tab there too: the service worker knows devknobs' frame by its first load (`webNavigation.onBeforeNavigate` for a frame under the top one, to the page's own address), and once it lands on another origin of the same site (`onCommitted` or `onErrorOccurred`) asks the page for its knobs (`carry`), loads that address in the tab, and hands the knobs to the tab's next page on that origin, within 30 seconds, with its first `get`; a load of another address in the tab meanwhile, or the frame closing, drops them. A redirect to another site, or a later load sent to another host, still gets devknobs' notice, whose button closes the frame. With the panel closed and no handle, the toolbar button opens it on any page, a framed one too.

## Build and load

```sh
pnpm --filter @vinena/knobs build
pnpm --filter @knobs/extension build
```

The content script bundles devknobs' built package, and `dist/` gets its device images. Then in Chrome: `chrome://extensions`, turn on Developer mode, Load unpacked, pick `packages/extension/dist`.

A local build sets the manifest's `version_name`, and the panel footer, to `<version> · local <label> (<short sha>[+dirty])`: the label is `KNOBS_BUILD_LABEL`, else the branch, else the worktree folder. `CI=true` and `package` builds keep the plain version.

Local builds reload themselves when you rebuild: the service worker checks `dist/build.json` and reloads the extension when it changes. Release builds have no `build.json` and no `alarms` permission.

## Store

`pnpm --filter @knobs/extension package` builds `dist/` and zips it to `devknobs-<version>.zip` here (gitignored), the file the Chrome Web Store takes. The version is the manifest's, the devknobs release it bundles. `store/listing.md` holds what the store's dashboard asks for (text, permission justifications, privacy answers), and `store/` the screenshots and the promo tile. The icons are `static/icon-*.png`, from the logo master (see `AGENTS.md`, "Logo"); the 128 is the logo at 96px in 16px of clear space.

## Checks

- `pnpm --filter @knobs/extension test`: the knob to CDP command mapping (`src/knobs.ts`), the headers and override per ua preset (`src/ua.ts`), what a detach tells the tab and how kept edits are read (`src/messages.ts`) and the record of a frame's load and the line it gives (`src/refusal.ts`), with `bun test`.
- `pnpm --filter @knobs/extension smoke`: loads `dist/` into Playwright's Chromium, drives the panel through `window.devknobs` on a local page and checks what the page sees, in the width knob's frame too, then resets and checks the debugger is off. A page whose policy allows no inline style, and one with `style-src 'self'; style-src-attr 'none'`, gets the panel styled as on any page. Then a page themed from `matchMedia` change events and `light-dark()` flips with the scheme knob, docked too, while the panel keeps the system's look; a page that sends `X-Frame-Options: DENY` and `frame-ancestors 'none'` loads in the frame, in a new tab opened straight to it too, and the framing rule is in only while devknobs' frame is open, its own tab's and host's: with none open, a page's own frame keeps `X-Frame-Options` and its CSP sandbox. The panel shows no handle while closed, where the npm build does. In a window of its own, a plain size and a phone with nothing drawn are the tab's own viewport (its width, ratio and touch screen, no frame, no reload), a mock or a browser drawn around the phone brings the frame back with the override cleared, and reset detaches. In-page mode in a window of its own: the switch off detaches the debugger and the page emulates text size (inline on `<html>`) and frames a plain phone, every knob kept; on again, the debugger is back and the inline size gone; closing Chrome's bar, run through the service worker's handler since a test cannot click the bar, turns it off for every tab with the knobs kept. A link in a frame to another origin moves the tab there. A page whose app takes devknobs' nodes out of `<body>` as it starts, or puts a new `<body>` in, keeps its frame and panel. Why a frame was refused, in a profile of its own: a page that refuses frames, with the framing rule taken off, shows that the debugger was not watching, and "find out why" names its `frame-ancestors` and copies a record with the status, headers and `Sec-Fetch-*`, then the debugger leaves; a frame redirected to another host names that host; a service worker's `X-Frame-Options` answer says it came from one, with its scope; in-page, it says to turn real browser settings on. It shoots that notice to `smoke-out/refusal-cause.png`. Service workers, in a profile of their own: a page whose worker fetches it from a server that refuses frames loads in the frame with no notice, real and in-page, with the worker rule on its host while the frame is open, gone once the frame closes and once the tab closes; a worker that answers from its cache says so under the notice, and its button loads the page past the worker, with a knob on and with none, then closing the frame turns the bypass off and the debugger leaves. The same with a mocked phone on pages whose app clears `<body>` as it starts, puts a new one in, or reloads the tab once the frame's copy loads past the worker: the frame ends up showing the page with the bypass on and the debugger attached, and both go with the frame. What servers see, in a profile of its own: a page with a service worker, under the ua knob, sends the preset's user agent and client hints (none for iPhone Safari; `?1` and `"Android"` for Android Chrome) on its load, a fetch, an image and a fetch its service worker makes, with no debugger, in real mode with it (where the page and a worker of its read the same) and in-page; another tab keeps Chrome's own; an iPhone 18 Pro's frame loads as Android Chrome after the ua knob picks it; the ua knob goes to the tab's own host only, never to the page's service worker or another host; a device in the frame sends Chrome's own everywhere while the frame's `navigator` reads the iPhone, and real phone mode sends the iPhone on the frame's page loads alone and turns in a tab on another host too; turning the ua knob or a whole-tab device off loads a page loaded under it again as Chrome; closing the panel from the toolbar leaves no rule and a reload no device; system puts Chrome's own back and drops the rules. A page that mounts devknobs' module build itself, with a hotkey and grab's color of its own, keeps one panel, the extension's, with the page's hotkey and color, and the page's `unmount()` leaves it; a copy that claims the page as 0.3.0 does is taken over and its panel goes. Prefer, in a profile of its own, on a page that mounts a local build of devknobs (the module build served with a `-local.123` version): extension keeps one panel, the extension's, its footer `extension <version>`; picking page in its settings hands the page over at once, one panel, the page's, its footer `page <version>-local.123`, with no take-back, through a load again too; a page with no copy of its own keeps the extension's; the page's knobs set in its panel last a load again; the page unmounting its copy and the toolbar button bring the extension's panel back, open; picking extension in the page's panel loads the page again with the extension's. It shoots both settings to `smoke-out/prefer-extension.png` and `prefer-page.png`. Shortcuts, in a profile of its own: shift j recorded for grab in the settings on one origin is kept in `chrome.storage.local` and grabs on another origin, in a tab open already with no load again, in one opened after, and in devknobs' frame with the focus in it; a page script with no gesture, through the bridge's event or the store on the window, leaves storage as it was. The npm build on a page with `style-src 'self'; style-src-attr 'none'` draws the same pixels as on one with no policy, with the panel open, a knob's editor open, grab's overlay, a refused frame's notice and a phone's mock. It also shoots the open panel with the extension and with the npm build, and the settings with the switch, into `smoke-out/`. Build first. `bun scripts/build.ts <dir>` and `node scripts/smoke.ts <dir>` build and check another directory than `dist/`, so a work in progress never lands in the one Chrome loads. Needs Playwright's Chromium (`pnpm exec playwright install chromium`); branded Chrome ignores `--load-extension`. CI runs it on every PR, on local pages only.
